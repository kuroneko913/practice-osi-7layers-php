# なぜL2スイッチだけでは足りず、L3が必要なのか

[L2スイッチと4台のPC実験](L2SwitchAndLimits.md) で行った実験を振り返り、実際に観測した結果を根拠に、L2（データリンク層）だけでネットワークを作ったときの限界と、L3（ネットワーク層）が必要になる理由を整理します。

一般論としての限界は [L2SwitchAndLimits.md の「4. L2レイヤーの限界」](L2SwitchAndLimits.md) にまとめています。このドキュメントでは、それを実験で確かめた結果としてまとめ直します。

---

## 1. 結論

L2スイッチは、**少人数のネットワークの中でフレームを届ける**ことは得意です。しかし、次の3つの理由で、それだけでは大きなネットワークを作れません。

1. **全員に届く通信（ブロードキャスト、フラッディング）が、ネットワーク全体に広がる**
2. **ネットワークを分けると、今度は分けたネットワーク同士で通信できなくなる**
3. **フレームには寿命がなく、ループすると止まらない**

VLANを使うと1は小さくできますが、その代わりに2が起きます。**分けたネットワークの間をつなぎ、行き先を判断する役割**がL3（ルーター）です。

---

## 2. L2スイッチで実現できたこと

まず、L2だけで実現できたことを確認します。

| できたこと | 実験 |
| :--- | :--- |
| 送信元のMACアドレスを学習し、宛先のポートにだけ届ける | `unknown_unicast.php`、`known_unicast.php` |
| 壊れたフレームを転送しない | `invalid_frames.php` |
| ケーブルが抜けたポートへは転送しない | `link_state.php` |
| ARPでIPアドレスからMACアドレスを調べ、IPv4パケットを届ける | `arp.php`、`ipv4.php` |
| VLANでネットワークを分け、トランクで2台のスイッチをまたいで延ばす | `vlan.php`、`vlan_trunk.php` |

4台のPCを1台（または2台）のスイッチでつなぐ規模なら、L2だけで十分に通信できました。問題は、規模が大きくなったときと、ネットワークを分けたときに現れます。

---

## 3. 実験で見えたL2の限界

### 限界1: 全員に届く通信が、ネットワーク全体に広がる

L2スイッチは、宛先を知らないフレームとブロードキャストを、受信したポート以外の**すべてのポート**へ送ります。

| 観測したこと | 実験 |
| :--- | :--- |
| PC-AのブロードキャストがPC-B、C、Dの全員に届いた | `broadcast.php` |
| 宛先を学習する前の通信が、無関係なPC-C、Dにも届き、NICで破棄された | `unknown_unicast.php` |
| PC-Cは、自分に関係のないARPリクエスト（`Who has 192.168.1.2?`）を毎回受信して処理した | `arp.php`、`node.php` での手動実験 |

4台なら負担は小さいですが、ARPのように**通信を始めるたびにブロードキャストを使う**仕組みがあるので、台数が増えるほど全員の負担が増えます。L2スイッチには、この「全員に届く範囲」（ブロードキャストドメイン）を区切る手段がありません。

### 限界2: 全員に届くので、盗聴やなりすましがしやすい

フラッディングされたフレームは、NICの設定を変えれば誰でも読めます。スイッチは送信元のMACアドレスも検証しません。

| 観測したこと | 実験 |
| :--- | :--- |
| プロミスキャスモードのPC-Dが、フラッディングされたPC-A宛ての通信を読めた | `flood_sniffing.php` |
| PC-DがPC-AのMACアドレスを名乗るだけで、スイッチの表が書き換わり、PC-A宛てのフレームを横取りできた | `mac_spoofing.php` |
| 偽の送信元で表を埋めると、スイッチが学習できなくなり、すべての通信がフラッディングされて読めた | `table_overflow.php` |
| PCの接続を入れ替えると、スイッチは古い情報のまま、別のPCへフレームを届けた | `port_swap.php` |

特に `port_swap.php` では、**誰もエラーを出さないまま、宛先のPC-Aにはメッセージが届かず、別のPC-Cに届きました**。送信したPC-Bも「送信完了」と表示しただけで、誤配に気づけませんでした。

### 限界3: アドレスに階層がなく、表を1台ずつ覚えるしかない

MACアドレスは、製造時に割り当てられる識別子で、**場所を表していません**。そのためスイッチは、通信した機器を1台ずつ表に覚えるしかありません。

| 観測したこと | 実験 |
| :--- | :--- |
| 表の容量（実験では4件）を超えると新しい機器を学習できず、フラッディングが続いた | `table_overflow.php` |
| PCが移動しても、本人が送信するまでスイッチは古い場所へ送り続けた | `station_move.php` |
| 古い情報はエージング（実験では2秒）で消えるまで残り、その間は届かなかった | `aging.php` |

2台のスイッチをトランクでつないだ実験では、スイッチ2はPC-Aの本当の場所を知らず、「トランクの先にいる」と覚えるだけでした。それでも、**PC-Aという1台の機器を、スイッチ2の表に1行ずつ覚える必要がある**ことに変わりはありません。世界中の機器をこの方式でつなぐと、すべてのスイッチがすべての機器を覚えることになり、表が破綻します。

### 限界4: フレームには寿命がなく、ループすると止まらない

| 観測したこと | 実験 |
| :--- | :--- |
| 同じスイッチの2ポートをケーブルでつなぐと、**1通のブロードキャストが2秒で約580回**ケーブルを通過し、全PCに約580個ずつ届き続けた | `loop_storm.php` |
| 戻ってくるフレームの送信元を見て、スイッチがPC-AのMACアドレスの場所を580回書き換えた（MACフラッピング） | `loop_storm.php` |
| ループの中にARPリクエストを流すと、届くたびにPC-Dが応答し、応答まで大量に発生した | `cable.php` での手動実験 |
| ケーブルを抜くまで止まらなかった | `loop_storm.php` |

Ethernetのヘッダには、何回中継されたかを数える欄（TTL）がありません。スイッチには、フレームが同じ所を回っていることを知る手段がないのです。

## 4. VLANで分かったこと: 分けると、つながらなくなる

限界1、2への対策として、VLANを実装しました。

| 観測したこと | 実験 |
| :--- | :--- |
| VLAN 10のブロードキャストは、VLAN 20のPCに届かなくなった | `vlan.php` |
| プロミスキャスモードのPC-Dでも、別のVLANのフレームは届かないので読めなくなった | `vlan.php` |
| トランクで2台のスイッチをつなぐと、別のスイッチにいる同じVLANのPCには届いた | `vlan_trunk.php` |

VLANは、**ブロードキャストが届く範囲を区切る**ことに成功しました。限界1と2の影響を、同じVLANの中に閉じ込められます。

しかし、同時に新しい問題が生まれました。

| 観測したこと | 実験 |
| :--- | :--- |
| PC-A（VLAN 10）からPC-C（VLAN 20）へ、MACアドレスを指定して送っても届かなかった | `vlan.php` |
| IPアドレスで送ると、ARPリクエストがVLAN 10の中にしか流れず、PC-CのMACアドレスを解決できなかった | `vlan.php`、`node.php` での手動実験 |
| 同じスイッチにつながっていても、VLANが違うと通信できなかった | `vlan.php` |

ARPは、ブロードキャストが届く相手しか見つけられません。そのため、**ブロードキャストが届く範囲を区切ると、その外にいる相手とは通信できなくなります**。L2の仕組みの中には、区切った範囲の外へ出る方法がありません。

VLANは「部屋を分ける壁」で、壁を作っただけでは部屋の間を行き来できない、ということです。

## 5. L3（ルーター）が解決すること

ここまでの限界に、L3がどう対応するかをまとめます。L3の部分はまだ実装していないので、実装して確かめる予定の内容です。

| L2の限界 | L3での解決 |
| :--- | :--- |
| 分けたネットワーク同士で通信できない（VLAN） | **ルーター**が、ネットワークの間でパケットを中継する。PCは別のネットワーク宛てのパケットを、ルーター（デフォルトゲートウェイ）のMACアドレス宛てに送る |
| ブロードキャストが全体に広がる | ルーターはブロードキャストを中継しない。ネットワークの境界になり、ブロードキャストが届く範囲を適切な大きさに保てる |
| アドレスに階層がなく、全機器を覚える必要がある | IPアドレスは「ネットワーク部」と「ホスト部」に分かれる。ルーターは「192.168.20.0/24 宛てはこちら」のように、**ネットワーク単位で**行き先を覚えればよい |
| フレームに寿命がなく、ループすると止まらない | IPヘッダには **TTL** があり、ルーターを通るたびに1減り、0になると破棄される。ループしても永遠には回らない |
| 部署の間の通信を制御できない | すべての通信がルーターを通るので、そこで通す通信と通さない通信を決められる（ファイアウォール） |

### L3でも解決しないこと

L3は万能ではありません。次の問題は、L3を入れても残ります。

- **同じネットワークの中の盗聴やなりすまし**: ルーターを通らない通信は、今までどおりL2の世界で届きます。ARPの応答も検証されないので、偽のARP応答で通信を横取りする攻撃（ARPスプーフィング）も考えられます。
- **通信の中身の保護**: どの層でも、届いてしまえば中身は読めます。内容を守るには、暗号化（TLSなど）が必要です。

そのため実際のネットワークでは、VLANで分け、ルーターでつないで制御し、暗号化で中身を守る、というように**層ごとの対策を重ねて**使います。

## 6. 次に作るもの

VLAN 10と20の間をつなぐルーターを作ります。今回のトランクの仕組みをそのまま使えます。

```text
                    [ルーター]
                        │ トランク (VLAN 10 と 20 をタグで運ぶ)
                  [スイッチ]
                  │        │
          VLAN 10: PC-A    VLAN 20: PC-C
       192.168.10.0/24     192.168.20.0/24
```

実装して確かめたいことは次のとおりです。

- **VLANごとにIPアドレスの範囲（サブネット）を分ける**: 今は全員が `192.168.1.x` なので、VLANに合わせて分け直す
- **デフォルトゲートウェイ**: PCが、宛先が自分のネットワークの外にあると判断して、ルーターのMACアドレスへ送る
- **MACアドレスの書き換え**: 同じIPパケットでも、ルーターの前後で送信元と宛先のMACアドレスが変わる様子をWiresharkで見る
- **TTL**: ルーターを通るたびにTTLが1減ることを確かめる
- **ブロードキャストの遮断**: VLAN 10のARPリクエストが、ルーターを越えてVLAN 20に届かないことを確かめる
